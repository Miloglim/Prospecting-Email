# 运价查询三段式规则（机械匹配 → 模型语义重试 → 分清的"没有"）

日期：2026-09-07　状态：规范已定，代码待落
起因（用户实测钉出来的）：问「地东的价格」，助手回「镜像库暂无地中海航线的报价记录」，
还反过来要用户补起运港与柜型。而真源（局域网台账 board_server）里就有地东航线、目的港伊斯坦布尔
的报价。两处不对：

1. **把"查不到"说成"没有"**。本地镜像只有 428 行、lane 仅加勒比/南美东/墨西哥/南美西/中美洲，
   这台机器的镜像根本没跟上真源 —— 该说的是"本地镜像里没有、可能没同步"，不是"无此航线"。
2. **机械匹配只认字段猜值**。`quote_search` 要求模型自己决定把「地东」填 `lane` 还是 `pod`：
   填 lane → `like(lane,'%地东%')`；填 pod → `like(pod_raw,'%地东%')`。而台账里目的港被拍平成
   `ISTANBUL 伊斯坦布尔(土耳其) 地东` —— 航线小字粘在目的港尾巴上，两个字段哪个都可能对不上。
   同一份数据在运价页手敲"地东"却能筛出来（页面直接 `LIKE %地东%` 打 pod_raw）。

## 0. 红线

1. 模型可见的入参与返回字段**只增不改**：`lane`/`pod`/`carrier`/`container` 语义不动，新增 `q`。
2. 三段式只是**查询与话术**的分层，不得给 agent 新增任何写/外发能力（同步仍只有运价页那颗按钮）。
3. 候选值一律**实时取自镜像**（`GROUP BY` 现算），禁止把"地东/地中海/欧地"这类词硬编成第二份词表。
4. 话术里的数字必须来自工具返回（行数、最近同步时间、命中数），模型不得自己估。

## 1. L1 机械层：一个词跨字段并集，不靠模型猜

`QuoteFilters` 新增 `terms?: string[]`：每个词的条件是
`(lane LIKE %t% OR pod_raw LIKE %t% OR pol LIKE %t%)`，词与词之间 AND；
`lane`/`pod` 各自的 AND 精滤语义保留（页面与"某航线到某港"类查询仍用它们）。

`quote_search` 的取值规则（实现口径，2026-09-07 定）：

- **每个词各自成为一个跨字段 OR 组，词与词之间 AND**：`q`、`lane`、`pod` 三个入参里给了哪些词，
  就把每个词分别铺成 `(lane OR pod_raw OR pol)`，不再由 `lane` 单列做精滤——单列精滤正是脏 lane
  （航线名粘在目的港尾巴、lane 列为空）会漏一次的原因；
- 词在进 `terms` 前各过一次 `resolveQueryPod`（原始词与标准港名两个写法都进，同词去重），
  原 `pod` + `podRawExpansion` 的航线级展开分支保留（查 SANTOS 仍要命中 pod_raw=「南美东」的行）；
- 词本身先过现有归一：去「航线/线」口语尾巴 → `resolveQueryPod`（港口别名/代码）→ `podRawExpansion`。

`pod` 的字段描述同步改成「目的港或航线关键词（中英文均可，工具会同时比对目的港与航线）」，
不再写"英文港名"——那正是把「地东」挤进 `lane` 的原因。

## 2. 数据层：入库时剥离目的港尾巴上的航线标签

`mapRemoteRow` 在写库前剥 `pod_raw` 尾部粘连的航线标签，规则（按序）：

1. 尾词与该行 `route`/`lane` 值相同 → 剥掉（台账里最常见的形态：小字就是航线名）；
2. 尾词命中受控区域词表 `LANE_TAGS`（地东/地西/欧地/欧西/地中海/黑海/波海/红海/波斯湾/阿拉伯海/
   南亚/东南亚/西非/东非/北非/大洋洲/北欧/波罗的海 + 现有 lane 枚举值）→ 剥掉；
3. 剥下来的标签若该行 `lane` 为空 → 用它回填 `lane`；已有 lane 则只剥不填；
4. 只剥**最后一个空白分隔的尾段**，且尾段长度 ≤ 6 字、不含括号（防把 `BALBOA, PA 巴尔博亚(巴拿马)`
   这类"英文港名 + 中文译名(国家)"的正常形态切碎）。

界面与工具看到的 `pod_raw` 因此不再带小字；航线信息回到它该在的 `lane` 列。
镜像是全量刷新的（`sync()` 每次重建），无需回刷历史脏行；运价页与 `rates-standard.json` 建表脚本
的 `unresolvedPods` 清洗入口不动。

## 3. L2 语义层：空结果必须带"库里到底有什么"

`total === 0` 且本轮第一次调用（`ctx.counts` 里 `quote_search` 计数 = 1）时，返回：

```
candidates: {
  lanes: [{ v: "加勒比", c: 222 }, …],   // 实时 GROUP BY lane，含计数，空值记「未标注」
  pods:  [{ v: "ISTANBUL 伊斯坦布尔(土耳其)", c: 3 }, …],  // GROUP BY pod_raw，按与查询词的贴合度取前 12
}
mirror: { rows, lastSyncAt, remoteHost, reachable, lastError }   // reachable = 现场探测台账，仅未命中路径才探
notice: 指令 = ①从 candidates 判断用户的说法是否对应其中某个航线/港（含"地东≈地中海东部、伊斯坦布尔属地东"这类常识）
             ②命中则换词再查一次（允许且仅允许一次重试）③对不上则进 L3，禁止直接说"没有"
```

贴合度排序用最机械的一条：查询词与 `pod_raw` 有公共子串（≥2 字）优先，其次含中文译名者，再次按计数降序。
语义判断交给模型，代码不做同义词表。

## 4. L3 定论层：三种"没有"分开讲

第二次调用仍 `total === 0`（计数 ≥ 2）时，按 `mirror` 判定，notice 只给一条路走：

| 现场 | 结论话术（工具预置，模型照说） | 出口 |
|---|---|---|
| `reachable === false` 或 `lastSyncAt` 距今 > 24h 或 `lastError` 非空 | 「本地镜像里没有（共 N 条，最近同步 T），局域网台账现在连不上/镜像是 T 前的，很可能没跟上真源」 | 动作卡「去运价页点同步」+ 允许问用户要不要联网调研 |
| 镜像新鲜且可达 | 「台账里确实没有这条航线/这个港口的报价」 | 才问「要不要我联网查当前市场行情？」 |

任何一段都不许出现"镜像库暂无该航线报价"这类把查询失败当数据缺失的措辞；
旧 notice 里那句「不要重复调用本工具」改成「第一轮没命中请按 candidates 换词重试一次」。

## 5. 验收

- 单测（`tests/unit/rates-query-fallback.test.ts`，sql.js 沙箱 + `BASE_SCHEMA_SQL`，插带尾缀与 lane 为空的模拟行）：
  1. `mapRemoteRow`：`pod_raw="ISTANBUL 伊斯坦布尔(土耳其) 地东", route=""` → `podRaw` 无尾缀、`lane="地东"`；
     尾段是 `(巴拿马)` 这类带括号形态时不剥；`route="地东"` 时按规则 1 剥并保留 lane。
  2. L1：`q="地东"` 命中该行（并集），`lane="地东"` 也命中；页面式 `pod="伊斯坦布尔"` 命中。
  3. L2：`q="不存在的港"` → 第一轮返回 `candidates.lanes` 含真实 lane 与计数、`notice` 含"换词再查一次"。
  4. L3：同参数第二次调用 → notice 出现"镜像/同步/联网"三种关键字之一，且不再给 candidates。
- 既有 `rates-normalize.test.ts` 的 `podRaw` 原样断言（MANZANILLO / PANAMA 复合港名）必须仍绿——即规则 4 的长度与括号护栏有效。
- 全量：`npm run typecheck` + `npm test` + `npm run build` 三绿。
- 手测（本机连不上那个局域网，只能验"连不上真源"这一支）：问「地东的价格」→ 应回答本地镜像没有、
  台账连不上、给出运价页同步出口，而不是"暂无该航线报价"；问「加勒比的价格」→ 与改前一致正常出表。
